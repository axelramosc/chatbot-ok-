# 1. Objetivo
Un interruptor global en el CRM que apaga a Ava en TODOS los canales (WhatsApp, Messenger, Instagram).
Con el bot apagado, cada cliente que escriba recibe un mensaje fijo que lo redirige / pide que se
comunique al **844 273 9524**. Los mensajes del cliente se siguen guardando y se ven en la bandeja.

# 2. Revisión de la estructura actual (hallazgos)
- Entrada: `app/api/webhook/route.ts` (WhatsApp) → `lib/message-handler.ts`;
  `webhook/messenger` e `webhook/instagram` → `lib/channel-handler.ts`. Son DOS pipelines casi duplicados:
  el interruptor debe ir en ambos.
- Hoy el único "pausado" es por conversación (`conversations.status` = attended / closed / sale_completed).
  No existe apagado global.
- El bot también habla sin que el cliente escriba: `app/api/cron/follow-up/route.ts` (diario 10:00) manda
  seguimientos a `sale_pending`. Un apagado global debe cubrirlo.
- `notifications.ts` avisa al admin por WhatsApp (venta, desconocido, representante). Esos avisos NO son
  al cliente; con el bot apagado ya no se generan porque no corre la IA.
- `/api/ava-command` (orden privada del equipo) y respuestas manuales (`send-message-v2`) son acciones
  humanas: se dejan funcionando.
- `business_settings` se vuelca COMPLETA al prompt (`ai.ts: buildBusinessContext`) y se pinta entera en
  `dashboard/settings`. Meter el flag ahí lo filtraría al prompt y lo mostraría como campo de texto
  → por eso se usa tabla propia.
- RLS: las demás tablas usan `authenticated_full_access`. `bot_control` será SOLO LECTURA para el CRM
  (escritura solo vía `/api/bot-control`), por hallazgo del Auditor.
- Regla #1 del repo: cambios ADITIVOS. Este contrato lo respeta (tabla nueva, ramas tempranas con retorno
  anticipado; con el interruptor en "encendido" el comportamiento es idéntico al actual).

# 3. Diseño
## 3.1 Datos (migración `supabase/migrations/008_bot_control.sql`, idempotente, aditiva)
```sql
create table if not exists bot_control (
  id int primary key default 1 check (id = 1),     -- fila única
  enabled boolean not null default true,
  redirect_phone text not null default '8442739524',
  updated_at timestamptz not null default now(),
  updated_by text
);
insert into bot_control (id) values (1) on conflict do nothing;
alter table bot_control enable row level security;
-- Solo lectura para el CRM; toda escritura pasa por /api/bot-control con service_role (S2/S3).
create policy bot_control_read on bot_control for select to authenticated using (true);
-- Si el banner usa Realtime: alter publication supabase_realtime add table bot_control;
```
Anti-spam por conversación: `conversations.context.bot_off_notice_at` (ISO). Sin columnas nuevas.

## 3.2 Backend
- Nuevo `lib/bot-switch.ts`:
  - `getBotControl()` → `{enabled, redirectPhone}`. Si falla la lectura: **fail-closed** (enabled=false) + `console.error`
    (decisión D2 de Axel: ante la duda, el bot queda apagado y se envía la redirección).
  - `buildRedirectMessage(phone)` → texto fijo (sin IA), p. ej.:
    "Hola 👋 Por el momento nuestro asistente virtual no está disponible. Para atenderte comunícate por favor
    al 844 273 9524 y con gusto te ayudamos. ¡Gracias!" (el copy final lo confirma Axel).
  - `shouldSendRedirect(context)` → false si `bot_off_notice_at` < 6 h (constante).
- `lib/message-handler.ts` y `lib/channel-handler.ts`: justo DESPUÉS de guardar el mensaje entrante y ANTES
  del chequeo de `status`/IA: si `!enabled` → (si `shouldSendRedirect`) enviar redirección por el canal
  correspondiente, guardarla como mensaje `bot`, actualizar `bot_off_notice_at`, y `return`. Sin llamar a Groq.
  El mensaje de error genérico del `catch` tampoco debe enviarse con el bot apagado, en AMBOS handlers
  (en `channel-handler.ts` hoy el `catch` no consulta estado: debe consultarlo). Errores al guardar
  `bot_off_notice_at` o al enviar la redirección se aíslan: no invocan IA ni el `catch` genérico.
- `app/api/cron/follow-up/route.ts`: si `!enabled` → responder `{skipped:"bot_off"}` sin enviar.
- `app/api/bot-control/route.ts` (nuevo, POST): exige sesión (mismo patrón de `ava-command`), valida
  `{enabled:boolean}`, escribe con service role y `updated_by = user.id`. El teléfono de redirección NO se
  acepta del cliente (fijo en BD; editarlo = migración/SQL), para no ampliar superficie.

## 3.3 UI (CRM)

- Toast de éxito/error; si falla el POST el switch vuelve a su valor previo.

# 6. Seguridad — Modelo de amenazas y criterios (S1–S11)

## 6.1 Modelo de amenazas (STRIDE)
- **Activos:** Disponibilidad del chatbot en los 3 canales (WhatsApp, Messenger, Instagram), integridad del número de redirección (`844 273 9524`), control de acceso al interruptor (`bot_control`), cuota/reputación en APIs de Meta y Groq, confidencialidad de credenciales y errores internos.
- **Actores:** Cliente externo (WhatsApp/Messenger/IG), atacante anónimo en Internet, usuario autenticado del CRM (legítimo, comprometido o malicioso), cron de Vercel (`CRON_SECRET`), servicios externos (Meta Webhooks, Supabase, Groq).
- **Superficie:** `POST /api/bot-control` (y `GET /api/bot-control` si se expone), tabla `bot_control` + política RLS + Supabase Realtime, `lib/bot-switch.ts`, `lib/message-handler.ts`, `lib/channel-handler.ts`, `app/api/cron/follow-up/route.ts`, UI del switch/banner en `app/dashboard/layout.tsx`.

| # | Amenaza (STRIDE) | Escenario concreto | Impacto | Control requerido |
|---|---|---|---|---|
| T1 | **Spoofing / Elevation of Privilege** — Auth de `/api/bot-control` | Atacante anónimo envía `POST /api/bot-control` con `{"enabled":false}` (o `GET` para sondear estado operativo) sin cookie válida, o fuerza un CSRF desde otro sitio contra un operador con sesión abierta. | Apagado/encendido no autorizado del bot en todos los canales. | Verificar sesión con `sessionClient.auth.getUser()` (401 si no hay usuario; sin fallback a `SERVICE_ROLE_KEY`). Exigir `Content-Type: application/json` y validar `Origin`/`Host` en `POST`. |
| T2 | **Tampering / Elevation of Privilege** — RLS `authenticated_full_access` en `bot_control` | Con la política `FOR ALL TO authenticated USING (true) WITH CHECK (true)` propuesta en §3.1, cualquier usuario autenticado abre la consola del navegador y ejecuta `supabase.from('bot_control').update({ redirect_phone: '<teléfono fraudulento>', updated_by: 'otro' })` o `delete().eq('id', 1)` vía PostgREST, saltándose `/api/bot-control`. | Desvío de clientes a un teléfono malicioso (fraude/suplantación) o borrado de la fila de control. | Cambiar RLS de `bot_control` a **solo `SELECT`** para `authenticated` (ninguna política de `INSERT`/`UPDATE`/`DELETE` para `anon` o `authenticated`). Toda escritura ocurre únicamente server-side con `service_role` en `/api/bot-control`. |
| T3 | **Repudiation / Elevation of Privilege** — Desactivación maliciosa por usuario autenticado | Un usuario interno malicioso, una cuenta comprometida o cualquier persona si Supabase Auth tuviera registro público abierto apaga el bot sin autorización o sin rastro atribuible. | Caída total de atención automatizada en los 3 canales y pérdida de ventas sin responsable trazable. | Deshabilitar registro público en Supabase Auth (solo altas por invitación/admin). Ignorar `updated_by` del body y fijar `updated_by = user.id` en servidor + log de auditoría. Definir con Axel si todo el equipo CRM puede conmutar o solo admins. |
| T4 | **Denial of Service / Integrity** — Fail-open ante fallo de DB o `catch` genérico | El equipo apaga el bot por incidente/cierre; un fallo transitorio de DB hace que `getBotControl()` devuelva `enabled: true` (fail-open) y Ava vuelva a contestar. Además, si falla la escritura de `bot_off_notice_at`, el error cae al `catch` externo de `message-handler.ts` o `channel-handler.ts` y envía el mensaje genérico de error al cliente. | Respuestas de IA no autorizadas cuando el bot debía estar apagado, o envío de mensajes erróneos al cliente. | Aislar errores no críticos (`bot_off_notice_at`) para que no disparen IA ni el `catch` genérico; validar en `catch` de ambos handlers que el bot no esté apagado; confirmar con Axel si acepta fail-open o prefiere fail-closed. |
| T5 | **Denial of Service / Abuse** — Spam del aviso de redirección y bucles | Un cliente manda múltiples mensajes simultáneos antes de que se guarde `bot_off_notice_at` (condición de carrera) generando múltiples avisos seguidos; o el cron `follow-up` sigue escribiendo / cambiando `status` a `active`; o un webhook falso intenta inyectar tráfico. | Bloqueo/degradación de calidad en Meta, spam al cliente y corrupción de `conversations.context`. | Mantener validación HMAC `x-hub-signature-256` en los 3 webhooks; descartar `is_echo`/estados; registrar `bot_off_notice_at` antes/atómico al envío preservando el resto de `context`; en `follow-up` salir sin enviar ni actualizar `status` si `!enabled`. |
| T6 | **Information Disclosure / Injection** — Fuga de errores, secretos o contenido no confiable | `/api/bot-control` filtra errores internos de Supabase/PostgREST; `SERVICE_ROLE_KEY` se filtra al cliente; o texto malicioso del cliente llega a Groq / se refleja en el aviso o en el DOM del CRM. | Exposición de esquema/llaves o XSS en el panel del CRM. | Respuestas de error genéricas (`500 Internal server error`), `service_role` solo en servidor, mensaje fijo sin entrada de usuario ni LLM, renderizado seguro en React sin `dangerouslySetInnerHTML`. |

## 6.2 Criterios de seguridad verificables (`S1`–`S11`)
- **S1 (Auth y validación en `/api/bot-control`):** `POST /api/bot-control` (y `GET /api/bot-control` si se expone) sin sesión válida responde `401` sin leer ni escribir `bot_control`, y nunca cae a `SERVICE_ROLE_KEY` para autenticar. Con sesión válida y body inválido (`enabled` faltante, string `"false"`, número o JSON inválido) o `Content-Type` distinto de `application/json`, responde `400` sin tocar la BD (prueba automática).
- **S2 (Integridad de campos y auditoría):** `POST /api/bot-control` solo modifica `enabled`; ignora o rechaza `redirect_phone`, `updated_by`, `id` y `updated_at` provenientes del cliente, asigna `updated_by = user.id` desde la sesión verificada y emite log estructurado con `user.id`, nuevo estado y timestamp (prueba automática).
- **S3 (RLS de `bot_control` solo lectura para cliente):** `bot_control` tiene RLS habilitado; `anon` no tiene acceso (`SELECT`/`INSERT`/`UPDATE`/`DELETE` denegados); `authenticated` tiene **únicamente `SELECT`** (cualquier `INSERT`/`UPDATE`/`DELETE` directo vía PostgREST/Supabase client falla por RLS, forzando toda escritura por `/api/bot-control` con `service_role`) (verificación SQL/PostgREST).
- **S4 (Control de alta y privilegios para evitar desactivación maliciosa):** Confirmado en Supabase Auth que el registro abierto (`Sign Up` público) está deshabilitado en producción; si existen usuarios del CRM que no deben apagar el bot global, restringir `POST /api/bot-control` por rol/allowlist definida por Axel (verificación de configuración / prueba automática si aplica allowlist).
- **S5 (Respuesta fija sin LLM ni reflexión/XSS):** Con `!enabled`, `buildRedirectMessage(phone)` devuelve texto fijo sin interpolar `text`, `contactName` ni datos de `conversations`; no se llama a `generateResponse` (Groq); el banner/switch/toast en `app/dashboard/layout.tsx` renderiza texto plano sin `dangerouslySetInnerHTML` (prueba unitaria + revisión).
- **S6 (Sin secretos ni fuga de errores internos):** Ninguna llave privada ni detalle interno de Postgres/Supabase (tablas, constraints, stack traces) aparece en respuestas HTTP ni en el bundle del cliente (prueba automática + revisión).
- **S7 (Anti-spam 6 h y protección contra ráfagas):** Con `!enabled`, mensajes múltiples del mismo cliente dentro de 6 h disparan como máximo 1 aviso de redirección; `conversations.context.bot_off_notice_at` se actualiza preservando las demás llaves (`customer_city`, `products_interested`, etc.) y evitando duplicados en ráfagas concurrentes; pasadas ≥ 6 h se permite reenviar (prueba automática).
- **S8 (Integridad de webhooks y prevención de bucles):** Los 3 webhooks (`whatsapp`, `messenger`, `instagram`) validan `x-hub-signature-256` antes de procesar; ecos (`is_echo`) y actualizaciones de estado se descartan antes del chequeo de `bot_control` (verificación en código / prueba).
- **S9 (Cron `follow-up` seguro cuando está apagado):** Con `bot_control.enabled = false`, `GET /api/cron/follow-up` (con `CRON_SECRET` válido) responde `{ skipped: "bot_off" }`, no envía mensajes salientes y no cambia conversaciones `sale_pending` a `active` (prueba automática).
- **S10 (Resiliencia FAIL-CLOSED y `catch` sin mensajes erróneos) — ACTUALIZADO por D2:** Si falla la lectura de `bot_control` o falta la fila `id = 1`, `getBotControl()` registra error en log y devuelve `enabled: false` con `redirectPhone` constante `'8442739524'` (el bot NO invoca a Groq). Si `!enabled` y falla guardar `bot_off_notice_at` o enviar la redirección, el `catch` externo de `lib/message-handler.ts` y `lib/channel-handler.ts` NO envía el mensaje genérico de error ni invoca a Groq (prueba automática).
- **S11 (Precedencia global sobre `/ava`):** Si el equipo usa `/api/ava-command` con el bot apagado (lo que deja `conversations.status = 'active'`), el siguiente mensaje entrante del cliente sigue siendo bloqueado por `bot_control.enabled = false` y no reactiva a Ava (prueba de integración).
